# 存储：缓存上限、数据库维护、日志轮换（1.0.12.0）

本地库（`%LocalAppData%\MailClient\mail.db`）里真正会增长的只有**已缓存的邮件正文**（`messages.BodyText` / `BodyHtml`，HTML 里的 `cid:` 内嵌图会被改写成 data URI 存进去，所以单封可以很大）和**日志文件**。1.0.12.0 给这两样都加了上限，并让 SQLite 文件能把空闲页还给磁盘。

## 1. 正文缓存上限

| 设置 | 默认 | 可选 | settings.json 字段 |
| --- | --- | --- | --- |
| 正文缓存保留时间（距上次打开 / 下载） | **90 天** | 30 / 90 / 180 / 365 天 / 不限制 | `BodyCacheMaxAgeDays` |
| 正文缓存大小上限 | **200 MB** | 100 / 200 / 500 MB / 1 / 2 GB / 不限制 | `BodyCacheMaxMb` |

`0` 表示不限制。读取时会夹到合理范围（天数 7–3650，大小 20–102400 MB；手改成别的值设置页会多显示一个“自定义”选项）。

### 清理策略（`BodyCachePlanner`，纯函数）

1. 先清掉**超过保留天数**的（`now - 最后访问时间 > 天数`）。
2. 剩下的总大小仍超过上限，就按**最久没打开**的顺序继续清，直到不超；时间相同的先清大的，再按 Id 排序，所以结果稳定。
3. “清理缓存”按钮 = 把所有允许清理的正文都清掉。

“大小”按 `BodyText + BodyHtml` 的 UTF-8 字节数计（`length(CAST(… AS BLOB))`）。

### 清理什么、不清什么

清理只做 `BodyText = NULL, BodyHtml = NULL, BodyFetched = 0`（并且 FTS 索引随触发器同步更新）。

**保留**：列表行（发件人 / 主题 / 预览 / 标志 / 时间）、附件元数据、你自己另存的附件文件、以及——因为无法从服务器恢复，或服务器还没收到你的改动——下面这些邮件的正文：

- 草稿（`IsDraft = 1` 或 Id 以 `draft:` 开头）
- 本地生成的已发送副本（`LocalState = 1`）和本地已移动、等待服务器重新同步的邮件（`LocalState = 2`）
- 在 `pending_ops` 里还有待写回操作的邮件（发件箱本身在 `outbox` 表里，不受影响）
- 演示数据账号

UPDATE 时会再检查一遍这些条件（清理期间状态变了也不会误清），每批 400 封。

### 清掉之后

邮件仍在列表里；再次打开时 `MessageBodyService.EnsureLoadedAsync` 发现 `BodyFetched = 0`，走原来的“按需拉取”从服务器重新下载并重新缓存（并更新访问时间）。被清掉的正文在重新拉取前**搜不到正文内容**（主题 / 发件人 / 预览仍可搜）。

### 最后访问时间（schema V7）

`messages.BodyAccessedAt`：保存正文时写入；阅读窗格加载一封已缓存的邮件时更新（后台、失败忽略）。同步的 upsert **不会**刷新它（用 `COALESCE` 保留旧值），否则每次同步都会把所有邮件“变新”，按时间清理就永远清不到。迁移时，已有缓存的正文回填成迁移时刻——升级后至少还有一个完整保留周期，不会一升级就被清掉。

## 2. 数据库维护（`StorageMaintenanceService`）

启动 20 秒后跑一次，之后每 6 小时一次，全部在后台线程（`Task.Run`，串行）：

1. 轮换日志（见下）。
2. 按当前设置清理正文缓存。
3. 数据库维护 `RunDatabaseMaintenanceAsync`：
   - **auto_vacuum**：新库建表前就设为 `INCREMENTAL`。老库不是 INCREMENTAL 时，做**一次** `VACUUM` 转换（`PRAGMA auto_vacuum = INCREMENTAL` 在连接上设好，VACUUM 时生效）。
   - `PRAGMA incremental_vacuum`：空闲页超过 1 MB 时把它们还给磁盘（很快，不重写整个库）。
   - 距上次完整 `VACUUM` 超过 60 天（`last-vacuum.txt`）时再做一次完整 VACUUM 整理碎片。
   - `PRAGMA wal_checkpoint(TRUNCATE)`：目前日志模式是 DELETE，所以是空操作；将来切到 WAL 不用再改。
   - VACUUM 前先检查磁盘空闲空间（需要约一个库大小的临时空间），不够就跳过并在返回值里说明。
   - VACUUM 前后各取一份 `messages.rowid` 指纹；如果 rowid 被重排（外部内容 FTS 依赖 rowid），自动重建 `messages_fts` / `messages_trgm`。（实测 SQLite 3.46 的 VACUUM 会保留 rowid，这是保险。）

VACUUM 期间持有数据库闸门，其他读写会短暂排队（几秒以内，数据库很大时更久），所以只放在后台和用户主动点“压缩数据库”时。

## 3. 日志轮换（`RotatingLog`）

`list-debug.log`、`sync.log`、`startup.log` 各自：单个文件超过约 **1 MB**（1,000,000 字节）就改名为 `.1`（原 `.1` → `.2`），**最多保留 2 份旧文件**，再从空文件写起；每个日志最多约 3 MB。写日志失败永远不会抛异常。启动时对历史遗留的超大日志也会轮换一次。（`sync.log` 之前是超过上限就整个删除，现在改为轮换保留最近的内容。）

## 4. 设置 → 存储

设置对话框有三页：通知 / 链接 / **存储**。存储页显示：

- 数据库文件大小（含可回收的空闲空间）
- 邮件正文缓存大小与封数（其中可清理的部分）
- 日志文件占用

并提供：保留时间、大小上限两个下拉框（改完立即保存并在后台按新上限整理一次）、**清理缓存**（点一下弹出确认气泡，确认后清空所有可清理的正文 + 回收空间 + 删除轮换出来的旧日志）、**压缩数据库**（完整 VACUUM）。

## 已知限制

- 正文被清理后，在重新打开（重新下载）之前搜不到正文里的词。
- 没有受管理的附件缓存：你另存到磁盘的附件不会被动；附件内容本来就不入库（只存元数据）。
- 只有服务器同步下来的正文可以被清理（本地发送副本 / 草稿 / 有待办操作的邮件没法从服务器恢复，所以保留）。
- 数据库较大时“压缩数据库”会占用几秒，期间列表可能短暂无响应。
